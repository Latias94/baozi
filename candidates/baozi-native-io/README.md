# baozi-native-io-candidate

Unpublished native filesystem and repository capture experiments for Baozi. This
package owns a standalone workspace, excluded from the root workspace. Its only
Baozi production dependency is `baozi-io`; the facade, import, core, and
postprocess crates do not depend on it. The facade is a development dependency
for public `Importer::read_asset` integration tests.

Native filesystem support remains `CandidateUnregistered`, with no
release-registered targets. Moving the implementation does not qualify a target
or change its dependency admission status.
Import sessions currently account for opaque open counts; native path/link/retry work is not yet
precharged through `WorkUnits`. The required pre-open bound remains a candidate qualification
gap alongside the platform matrix, rather than a guarantee supplied by this adapter.

## Runtime targets

The adapter accepts only these exact triples, including their ABI predicates:

- `x86_64-unknown-linux-gnu`
- `x86_64-pc-windows-msvc`
- `aarch64-apple-darwin`

Every other runtime target fails with an explicit compile error. Dependency
audits also resolve `x86_64-unknown-freebsd`; that profile does not enable a
runtime adapter. Browser WASM and WASI consumers use memory or custom IO through
`baozi-io`.

The native dependency baseline retains `cap-std`, its transitive
`cap-primitives`, and optional `cap-fs-ext` at `4.0.3`, and `rustix` at `1.1.4`.
Direct dependency default features remain disabled. `cap-fs-ext` explicitly
selects `std`; the Unix `rustix` edge selects `std` and `fs`. Native admission
checks still compare the reviewed target-specific dependency closures and
checksums. Preserve those versions when generating this workspace's lockfile.

## Opening assets

Open trusted host authority once, before processing untrusted logical paths:

```rust,no_run
use baozi_io::{AssetIo, AssetPath};
use baozi_native_io_candidate::{FileSystemAssetIo, NativeDirectoryCapability};

let capability = NativeDirectoryCapability::open_ambient("assets")?;
let io = FileSystemAssetIo::from_capability(capability);
let path = AssetPath::new("models/mesh.obj")?;
let mut opened = io.open(&path)?;
let mut buffer = [0_u8; 1024];
let bytes_read = opened.read_chunk(&mut buffer)?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

Applications can pass this adapter and a logical `AssetPath` to
`baozi::Importer::read_asset`. Request options and import policy remain owned by
the caller and import layer.

The native directory owner keeps its handle private. Clones share the retained
directory and authority identity; repository capture uses that same owner.
Opening, inspection, and reading stay bound to the returned file handle.
Metadata is a length hint, not an immutable-length or snapshot promise. Unix
opens remain nonblocking, and Windows reparse attributes are checked on the
opened handle, including unknown tags that otherwise look like regular files.

## Repository capture

The default feature set exposes filesystem IO only. Enabling
`repository-capture` adds the repository capture API and the optional
`cap-fs-ext` dependency. Capture retains its existing explicit roots, bounded
resource policy, same-object verification, and fail-closed behavior. On
`x86_64-pc-windows-msvc`, capture returns `UnsupportedIdentityBackend` before
traversal; enabling the feature does not claim an operational Windows capture
backend or release registration.

## Verification

Run the moved unit tests and public facade integration tests in this workspace,
both with `repository-capture` disabled and enabled. Reuse the root `target`
directory and serialize Cargo invocations with the root integration work:

```text
cargo nextest run --locked -j 1 --manifest-path candidates/baozi-native-io/Cargo.toml --target-dir target --no-default-features --test-threads 2
cargo nextest run --locked -j 1 --manifest-path candidates/baozi-native-io/Cargo.toml --target-dir target --no-default-features --features repository-capture --test-threads 2
```

These commands require the standalone lockfile generated by integration. Run
the suites on each runtime candidate; a host-only run does not establish the
other platforms' behavior. Preserve negative-target compile checks separately
from FreeBSD dependency auditing.

Tests retain the existing race, same-handle, held-child, symlink, nonblocking,
reparse, and repository controls. Windows tests require Python, actual junction
and unknown-tag reparse fixtures, and permission to create file symlinks. The
Python fixture is embedded from `src/fs/tests/windows_reparse.py`; fixture
failures are test failures, not skips.
